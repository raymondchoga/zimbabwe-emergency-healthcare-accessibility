Emergency Healthcare Accessibility Analysis in Zimbabwe
### A step-by-step QGIS methodology

**Scope:** national (Zimbabwe)
**Deliverables:** a set of maps + a written report
**Core questions:** How far are communities from emergency healthcare under normal conditions? Which communities are underserved? How does that picture change during flooding, when roads and bridges go down?

**Phase 4 — Baseline accessibility analysis: DONE (point-based; facility service-area polygons not yet generated, see note).**

- **QNEAT3 is not available** on this QGIS install (4.0.3 — a very new release) — the official plugin repository's compatibility-filtered XML doesn't list it yet (checked directly: fetched and rebuilt the full ~1,130-plugin repo index, no QNEAT3/"neat" match). Rather than wait on a compatible release, the equivalent analysis was built directly against QGIS's own network-analysis engine (the same one QNEAT3 wraps), run in the sandbox with `scipy.sparse.csgraph.dijkstra` for performance rather than through QGIS's Processing framework — see the numbers below for why (this needed to run against a graph with ~1.76 million nodes).
- **Method**: built a routable graph from the 30,619-segment merged road network — every vertex became a graph node (coordinate-snapped at 5m tolerance to merge near-duplicate nodes across the merged sources), giving **1,764,043 nodes / 1,773,753 edges**. 99.2% of nodes fell in one connected component (392 small disconnected islands, a road-data-quality artifact — facilities/points that happened to snap onto one of these were re-snapped to the nearest node in the *main* component instead of being falsely marked unreachable). Speed-per-class: trunk/primary 80 km/h, secondary 60, tertiary 40, unclassified 20, WFP "Road" 50, WFP "Trail" 15 (same scheme the original methodology specified). Ran one multi-source Dijkstra (`min_only=True`) seeded from all 1,500 facilities simultaneously — computes, for every node in the network, the travel time and identity of the *nearest* facility in a single pass (0.98 seconds). Each of the 15,894 population points was then snapped to its nearest graph node (median snap distance 1.3km, since points sit off-road by design; walking time for that snap gap is added at 4.5 km/h) and assigned that node's nearest-facility travel time.
- **Data-completeness caveat**: 1.9% of population points (representing ~46,000 people, 0.3% of national population) are >10km from the nearest mapped road — mostly in Hurungwe's remoter resettlement areas — meaning the road network genuinely doesn't reach them in the source data (OSM/WFP coverage gap, not a computation error). Their travel times are dominated by the walking-speed snap penalty and should be read as "very poorly served," not as precise drive times.
- **Result — driving scenario** (baseline, no flooding; **figures below are post-ZRP-correction, using the final 1,486-facility list** — see the Phase 2 health facilities note; the correction moved national totals by well under 0.1 percentage point, since only 1.1% of the population had a ZRP clinic as their nearest facility, but shifted results more meaningfully for those specific communities): **64.9% of the population (9.84M) well-served** (<30min), **21.0% (3.18M) underserved** (30–60min), **14.2% (2.16M) critical** (>60min or effectively unreachable). Sanity-checked against known geography per the Phase 8 guidance: Binga (65% critical), Kariba (73% critical), Tsholotsho (59% critical), Mbire (50% critical) — all Zambezi-valley/remote districts — came out worst as expected; Harare/Bulawayo/Chitungwiza averaged 3–9 minutes. This matches ground truth well.
- **Walking scenario added** — the driving-only numbers above assume vehicle access, which the user correctly pointed out is not realistic for much of rural Zimbabwe (walking, ox-drawn scotch carts, and informal "pirate taxis" are the actual common modes). Re-ran the exact same multi-source Dijkstra using a uniform **4.5 km/h walking speed on every road/track** (rather than the road-class-based driving speeds), keeping everything else identical (same graph, same facilities, same snap-distance handling — the off-road "last mile" was already walking-speed in both scenarios, so it's an apples-to-apples comparison of the on-road portion). Result (also post-ZRP-correction): **only 16.0% well-served (2.43M)**, **14.2% underserved (2.16M)**, **69.8% critical (10.60M)** on foot — median walking time to the nearest facility is **~3.7 hours**. The starkest finding is the *gap* between scenarios: roughly a third of the national population looks "well-served" if they have a vehicle but is in the critical (>60min) band on foot — this driving-vs-walking divergence is arguably a more important "who's underserved" signal than either scenario alone, since it identifies communities where accessibility entirely depends on vehicle ownership. Driving and walking are intended as the two realistic brackets (fastest plausible / slowest plausible) — actual experience for someone using a scotch cart or a shared taxi falls somewhere between the two, which this pair already brackets.
- Output: `data_processed/baseline_accessibility_5km_drive_and_walk.gpkg` (layer `baseline_accessibility`, supersedes the driving-only `baseline_accessibility_5km.gpkg` from earlier in this phase) — each point carries `drive_time_min`/`drive_class`/`drive_nearest_facility`, `walk_time_min`/`walk_class`/`walk_nearest_facility`, `snap_dist_m`, and `access_gap` (walk-class rank minus drive-class rank — flags the vehicle-dependency gap directly). Loaded into the live QGIS project as two separate layers pointing at the same file, "Accessibility - Driving" (visible, styled by `drive_class`) and "Accessibility - Walking" (hidden by default, styled by `walk_class`) — toggle visibility to compare.
- **Not yet done**: per-facility iso-area/service-area *polygons* (the classic "30/60/120-min band" cartographic output Phase 7 will want) — the point classification above answers the "who's underserved" question but doesn't yet produce polygon service areas for the map, for either scenario. Can be generated later (e.g. by buffering/dissolving reachable-edge sets per travel-time threshold, or revisiting once/if QNEAT3 becomes QGIS-4-compatible) — flagging so it isn't forgotten before Phase 7.

**Phase 5 — Flood scenario analysis: DONE (point-based, both modes; case-study routes and delta cartography still to come in Phases 6–7). Re-run once after the ZRP facility correction (see Phase 2 note) — figures below are the corrected/final ones.**

- **Method**: sampled the RP50 flood-depth raster (JRC/Copernicus, EPSG:4326, ~93m pixels, values only recorded where depth ≥0.1m) at the midpoint of every one of the 1,773,753 routing-graph edges (reprojecting midpoints to match the raster rather than reprojecting the raster itself, to avoid resampling artifacts). **17,656 edges (1.0% of the network) intersect the mapped flood extent** — mean depth among affected edges 2.5m, consistent with RP50 being a fairly severe/deep river-flood event concentrated in valley bottoms.
- **Flood-penalty rule** (explicit modeling assumption — stated here per the methodology's own instruction to document this as a choice, not a fact): depth <0.3m = passable with a heavy penalty (driving capped at 10 km/h, walking at 1.5 km/h); depth 0.3–1.0m = impassable by vehicle but still wadeable on foot (walking capped at 1.0 km/h); depth ≥1.0m = impassable for both modes, edge removed from both graphs entirely. Given the depth distribution above, most affected edges (12,966 of 17,656) land in the ≥1.0m "impassable for both" tier.
- Re-ran the identical multi-source Dijkstra setup from Phase 4 (same 1,500 facility sources, same population points) against these flood-penalized graphs — **16,377 edges become undriveable and 12,966 unwalkable** under this scenario.
- **Result — driving, flood vs. baseline**: well-served drops from 9.84M to 9.53M; hundreds of thousands of people see their driving accessibility class get worse, of which **323,420 people are cut off entirely** (were reachable at baseline, now disconnected from every facility by the flood). Newly-cut-off population concentrates in Chiredzi, Hurungwe, Chipinge, Lupane, Gokwe North, Beitbridge, Hwange, Tsholotsho, Mbire, and Victoria Falls — consistent with known flood-prone/remote geography (Save/Runde and Zambezi valley districts), passing the Phase 8 sanity check again. Checked the three named hotspots specifically at the user's request: **Muzarabani** loses 1,385 people (1.0% of its population) entirely, for both driving and walking, since the isolating segment floods past 1m and blocks both modes equally; **Kariba** (rural) is hit hardest proportionally — 2,568 people (5.1%) cut off driving, 2,196 (4.3%) walking, on top of an already-severe baseline (80min average); **Mount Darwin**, despite its flood-hotspot reputation, shows **zero** people cut off in this model — flagged as a result to sanity-check against local knowledge rather than trust blindly, since it may reflect real route redundancy or a mismatch between the JRC river-flood model and Mount Darwin's actual flood pattern.
- **Result — walking, flood vs. baseline**: 260,267 people are cut off entirely. Smaller than the driving impact in absolute terms mainly because so much of the walking baseline was already critical/unreachable before any flooding — there's less "room to fall."
- Outputs: `data_processed/flood_accessibility_5km.gpkg` (layer `flood_accessibility`) — each point carries baseline and flood time/class/nearest-facility for both modes (`drive_base_*`/`drive_flood_*`/`walk_base_*`/`walk_flood_*`), plus `drive_flood_delta`/`walk_flood_delta` (class-rank change) and `newly_cutoff_drive`/`newly_cutoff_walk` boolean flags for direct mapping. `data_processed/flooded_roads_RP50.gpkg` (layer `flooded_roads`, 17,656 line segments) carries `depth_m` and a `severity` label (light/moderate/severe) for cartography. **Network note for future sessions**: the cloud analysis sandbox can only reach GitHub raw/media content and package registries (pypi/npm) — HDX, WorldPop, JRC, ArcGIS, Overpass, ZimStat, plugins.qgis.org, etc. are all unreachable directly from the sandbox. The working pattern has been: user downloads/queries source data on their own machine (unrestricted internet) → shares via the device folder bridge → Claude processes/reprojects/clips/parses/routes in the sandbox → pushes results back and loads them into the live QGIS project via the QGIS plugin connection. For running network calls *through QGIS itself* (e.g. Overpass queries via execute_code): never block synchronously — it froze the app once. A background-thread-plus-polling pattern works for plain Python network calls (urllib/requests), but **does not work for QGIS's own Qt-based network calls** (e.g. the plugin repository fetch) — Qt's QNetworkAccessManager needs to be driven from the same thread that owns it, so a background thread just leaves a dangling, never-completing request. For those, call the async method directly on the main thread (it returns immediately without blocking) and poll for completion via separate, subsequent `execute_code` calls instead of an in-process wait loop. Large file transfers over the device bridge (>~20MB) are unreliable in one shot — split into smaller chunks/parts if a transfer times out. For extracting numeric data from PDFs, don't rely on WebFetch's summarization (it hallucinated at least one figure on this project) — download the actual PDF and parse it programmatically (pdfplumber worked well; watch for tables where the "Total" label lands on its own line below the numbers rather than prefixing them, which needs a two-pattern parser). For large-graph network analysis (routing/isochrones), `scipy.sparse.csgraph.dijkstra` with `min_only=True` is dramatically faster than either QGIS's native Processing algorithms (which are one-origin-at-a-time) or a pure-Python/networkx graph (which struggled to even build a ~1.7M-node graph quickly) — build the graph as a scipy sparse matrix and do multi-source shortest-path in one call.

## Phase 1 — Set up your QGIS project

1. Create a project folder on your machine with subfolders: `data_raw`, `data_processed`, `layouts`, `report`.
2. Open QGIS, create a new project, and immediately set the project CRS to **EPSG:32736 (WGS 84 / UTM zone 36S)**. This is a projected, metres-based CRS appropriate for Zimbabwe, and you need it for any distance/area calculation or network analysis to be accurate. (Most of your source data will arrive in EPSG:4326 / WGS84 lat-long — QGIS will reproject on the fly, but process/export everything into 32736 once you start measuring things.)
3. Save the project as `zw_health_access.qgz` in your project folder.

## Phase 2 — Source your data

You said you don't have data yet, so here's where to get each layer. All of these are free.

**Administrative boundaries** — Zimbabwe's official admin boundaries (COD-AB) are on the Humanitarian Data Exchange: search "Zimbabwe - Subnational Administrative Boundaries" on data.humdata.org. Gives you province and district polygons — you'll need these to report findings "by district" and to clip other datasets.

**Road network** — Download the Zimbabwe OSM extract from Geofabrik (download.geofabrik.de → africa → zimbabwe). Get the `.shp` or `.gpkg` roads layer. OSM road coverage in Zimbabwe is decent on trunk/primary roads, patchier on rural tracks — flag this as a limitation in your report later.

**Health facilities** — Two options, ideally use both and cross-check: (a) search HDX for "Zimbabwe Health Facilities" (a Ministry of Health & Child Care master facility list is sometimes hosted there or on the Zimbabwe HealthMap); (b) pull `amenity=hospital`, `amenity=clinic`, `amenity=doctors` points from the same OSM extract as your roads. For an *emergency* accessibility study, tag or filter to facilities that actually offer emergency/inpatient care if the attribute data allows it — a small rural clinic isn't equivalent to a district hospital.

**Population** — Use WorldPop's Zimbabwe gridded population dataset (www.worldpop.org, search "Zimbabwe", get the ~100m resolution unconstrained or constrained raster for the most recent year available). This gives you population distribution without needing to wait on census microdata. If you want administrative-level population, ZimStat's 2022 census report has district totals you can join to the boundary layer as a cross-check.

**Flood hazard / flood-prone areas** — A few options, pick based on what you want to show:
- *Historical event data*: Copernicus Emergency Management Service (emergency.copernicus.eu) has mapped extents for Cyclone Idai (2019, hit Chimanimani/Chipinge hard) and Cyclone Freddy (2023) — search their archive for Zimbabwe activations.
- *Modeled hazard*: JRC's Global Flood Hazard Maps or the WRI Aqueduct Floods tool give you flood-probability layers (e.g. 1-in-100-year river flood extent) covering the whole country, which is more useful for a "which areas are chronically flood-prone" framing than a single-event framing.
- *Rivers, as a proxy*: Zimbabwe's flood risk is concentrated along the Zambezi valley (Muzarabani, Kanyemba, Binga), the Save/Runde catchments, and parts of Manicaland (Chimanimani/Chipinge) — download OSM waterways as a supporting layer regardless of which hazard source you use.

## Phase 3 — Prepare and clean the data

1. Load everything into your QGIS project and reproject each layer to EPSG:32736 (Vector → right-click layer → Export → Save features as, choosing the CRS).
2. Clip all layers to the Zimbabwe national boundary so you're not carrying data from neighboring countries.
3. **Road network topology matters a lot for step 4.** OSM road data often has small gaps, overshoots/undershoots at intersections, and disconnected segments that will silently break network analysis. Run Vector → Geometry Tools checks, and consider the "Fix geometries" and topology-checking tools before proceeding. This is usually the most tedious but most important prep step — budget real time for it.
4. Decide how you'll represent "communities" for the accessibility analysis: either (a) convert the WorldPop raster to points via Raster → Conversion → Polygonize/Raster pixels to points weighted by population, or (b) use district/ward centroids from your admin boundaries as a coarser stand-in. Option (a) gives much finer-grained, more defensible results.

## Phase 4 — Baseline accessibility analysis

This is where you figure out, under normal conditions, how far each community is from the nearest facility.

1. Install the **QNEAT3** plugin (Plugins → Manage and Install Plugins → search QNEAT3) — it's the standard free QGIS tool for network analysis (shortest paths, service areas/isochrones, OD matrices) and works offline on your road layer. *(Not available on QGIS 4.0.3 as of this project — see Progress log above for the workaround used instead.)*
2. Assign a travel speed to each road segment based on its OSM road class (e.g. trunk/primary ~80 km/h, secondary ~60, tertiary ~40, unclassified/track ~20) using the Field Calculator — this lets QNEAT3 compute *travel time*, not just distance, which matters more for "emergency" accessibility.
3. Run QNEAT3's **Iso-Area as Polygons (from Point)** or **OD Matrix** tool from each health facility, generating drive-time bands (e.g. 30 min / 60 min / 120 min) — this produces your baseline "service area" map.
4. Overlay the population points/centroids from Phase 3 onto these service areas to classify communities: well-served (under 30 min), underserved (30–60 min), critical/very underserved (over 60 min or outside all service areas entirely). *(Done via a custom multi-source Dijkstra instead of QNEAT3, for both driving and walking — see Progress log above.)*
